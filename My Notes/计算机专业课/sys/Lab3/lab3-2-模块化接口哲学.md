# Lab3-2 笔记：模块化、接口与级联思想

## 1. 背景：为什么要模块化

硬件设计一旦规模变大，最怕的不是逻辑本身复杂，而是==变化会到处扩散==。

如果所有功能都写在一个大模块里，计数、进位、清零、边界判断全部混在一起，那么只要修改一个边界条件，很多地方都可能被牵连。这样写小实验能跑，大工程会直接失控。

模块化的目的不是单纯把代码拆成几个文件，而是把系统分成若干个==边界清晰==、==职责稳定==、==接口明确==的部分。每个模块只需要完成自己的职责，不需要知道自己被放在什么更大的系统里。

在 Lab3-2 里，`Cnt` 就是底层通用计数模块，`Cnt2num` 是上层组合控制模块。两者的关系正好体现了层次化设计的核心思想。

---

## 2. 核心思想：模块化不是拆代码，而是定义边界

`Cnt` 不知道自己被用在什么场景里。它不知道上层要做 10 进制、24 进制，还是别的 BCD 计数器。它只暴露三个关键接口：

| 接口 | 方向 | 语义 |
|---|---:|---|
| `co` | 输出 | 我满了，通知上层 |
| `low_co` | 输入 | 下层允许我走，我才递增 |
| `high_rst` | 输入 | 上层要求我清零，我就清零 |

这三个接口把两件事分开了：

- `Cnt` 内部只负责==如何计数==；
- `Cnt2num` 上层只负责==如何组织多个计数器==。

这就是模块化的本质：==内部实现和外部使用互不穿透==。上层不直接改底层寄存器，底层也不关心上层业务语义。双方只通过接口沟通。

真正强的模块不是“知道得多”，而是“知道得少”。`Cnt` 对外部越无知，它越容易复用。

---

## 3. 三个接口的本质作用

### 3.1 `co`：向上传递“我已经满了”

`co` 是底层向上层报告的信号。没有 `co`，高位计数器就不知道低位什么时候溢出，级联无法发生。

它的语义不是“让我递增”，而是“我已经到边界了”。这是一个==状态报告==信号。

### 3.2 `low_co`：向下接收“你现在可以走”

`low_co` 是当前位是否递增的触发条件。低位满了，高位才需要加一。

它和 `en` 不能混在一起：

- `en` 是整个计数系统的全局开关；
- `low_co` 是级联链条上传来的局部触发。

这两个信号分开，才能让模块既支持全局暂停，又支持局部级联。如果写死在一起，`Cnt` 就不再通用。

### 3.3 `high_rst`：上层对底层的统一覆盖权

`high_rst` 最关键。它不是因为 `Cnt` 内部一定需要，而是因为上层需要在某些情况下==无条件覆盖底层状态==。

比如 24 进制计数器的边界是 `23 -> 00`，不是两个模 10 计数器自然溢出的 `99 -> 00`。如果只靠 `co` 链，系统只能处理自然进位，无法处理这种非标准边界。

所以边界判断必须放在上层：

```systemverilog
wire judge = (high_cnt == 4'(HIGH_CO)) && (low_cnt == 4'(LOW_CO));
wire clear = judge && low_co && en;
```

上层发现已经到达 `23`，下一次触发时就通过 `high_rst` 广播清零。这样 `Cnt` 内部仍然是通用计数器，不需要写死“24”这个特殊知识。

---

## 4. 级联的本质：用简单模块组合复杂行为

级联不是简单地“把两个模块连起来”，而是利用接口语义让多个模块形成新的整体能力。

两个 `Cnt` 级联之后，低位负责个位，高位负责十位。低位满了通过 `co` 通知高位，高位通过 `low_co` 决定是否前进。上层再通过 `judge + clear` 处理 `23 -> 00` 的特殊边界。

这说明一个重要原则：

> ==底层保持通用，特殊规则放在上层。==

如果把“24 进制”写进 `Cnt`，它就只能服务这个实验；如果 `Cnt` 只提供通用接口，那么它可以继续用在 60 进制、100 进制、秒表、计数显示等其他场景。

级联的价值在于：底层模块能力很小，但组合之后能表达更大的系统行为。

---

## 5. 普适性、可替换性与工程化

接口设计得好，会自然带来两个结果：==普适性==和==可替换性==。

普适性指的是：同一个底层模块可以被放到不同场景里使用。`Cnt` 只承诺“收到驱动就计数，到边界就报告”，所以它能被复用。

可替换性指的是：只要接口行为不变，内部实现可以随便换。比如把 `Cnt` 内部从普通二进制计数改成格雷码计数，或者优化成另一种写法，只要 `co / low_co / high_rst / cnt` 的行为不变，`Cnt2num` 就不需要修改。

这就是工程化思想：

- 上层不依赖底层实现细节；
- 底层不依赖上层业务场景；
- 双方只依赖接口契约；
- 修改只发生在它应该发生的位置，不向外扩散。

硬件里叫==层次化设计==，软件里叫==解耦==，系统设计里叫==关注点分离==，本质是同一件事。

---

## 6. 复杂度为什么会下降

不模块化时，所有逻辑互相耦合，新增一个功能可能影响所有旧功能。复杂度近似随功能数量平方甚至指数增长。

模块化之后，每个模块内部复杂度被限制在局部，模块之间只通过有限接口相连。系统复杂度主要取决于接口数量，而不是所有内部细节的两两组合。

`high_rst` 是一个很好的例子。它把“24 截断”这个复杂性限制在上层一个地方，而不是扩散到每个 `Cnt` 的内部。这样后续修改边界时，只改上层判断，不改底层计数器。

这就是为什么工程上反复强调接口：接口不是形式，而是控制复杂度扩散的工具。

## 7. 调试坑：`localparam` 默认 32 位

实验中容易遇到 `WIDTHEXPAND` 报错：

```systemverilog
// 问题写法：HIGH_CO 默认是 32 位，high_cnt 是 4 位
wire judge = (high_cnt == HIGH_CO) && (low_cnt == LOW_CO);

// 修复写法：显式截成 4 位
wire judge = (high_cnt == 4'(HIGH_CO)) && (low_cnt == 4'(LOW_CO));
```

`localparam` 在 SystemVerilog 中默认是 32 位。拿 32 位常量和 4 位信号比较时，Verilator 会提示位宽扩展；如果 Makefile 使用 `-Wall`，warning 会被当成 error。

这不是编译器挑剔。位宽不一致可能掩盖真实硬件问题，比如本来只想比较低 4 位，却无意中触发了隐式扩展。硬件设计里，==位宽就是电路结构==，不能靠“编译器帮我猜”。

## 8. 思维提升：从计数器看到工程系统

这次实验表面上是在写 BCD 计数器，本质上是在训练工程化拆分能力。

一个好的系统不是靠一个大模块把所有事情做完，而是让每一层只知道自己应该知道的东西。`Cnt` 不知道 24 进制，反而让它更强；`Cnt2num` 不改 `Cnt` 内部，反而让组合更自由。

这种思想在计算机系统里到处都是：

- CPU 不知道运行的是游戏还是浏览器；
- TCP 不知道传输的是 HTTP 还是 SSH；
- 操作系统不需要知道应用内部算法；
- 函数调用者不应该依赖函数内部变量。

所以本实验真正要记住的不是 `co` 怎么连，而是这一条：

> ==接口稳定，内部自由；边界清楚，组合才强。==

---

## 9. 一句话总结

模块化的核心是定义边界，级联的核心是遵守接口。底层越通用，上层组合能力越强；上下层越互不穿透，系统越容易修改、扩展和维护。
