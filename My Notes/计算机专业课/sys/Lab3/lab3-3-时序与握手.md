# Lab3-3 笔记：时序思维与 start-finish 握手协议

## 1. 背景：为什么只有 `clk` 还不够

时序电路里，`clk` 解决的是**所有寄存器什么时候更新**的问题。它给整个电路提供统一节拍，让各个寄存器在同一个时间基准下工作。

但 `clk` 只能回答：

> 这一拍什么时候到？

它不能回答：

> 这个任务什么时候算完？

这两个问题不是一回事。

例如乘法器、除法器这类迭代模块，内部可能需要 32 拍才能完成一次计算。外部模块如果只看 `clk`，它知道时间在推进，却不知道结果什么时候有效。如果外部固定等 32 拍，看似能用，但这等于让外部知道了内部实现细节：内部必须刚好 32 拍完成。

一旦以后内部改成提前结束、变长迭代、流水线结构，外部逻辑就全部要改。

所以需要握手协议。

握手协议的目的不是替代 `clk`，而是在 `clk` 之上增加一层**任务级语义**：什么时候开始，什么时候结束，什么时候结果有效。

---

## 2. `clk` 和握手的分工

`clk` 和握手解决的是两个层面的问题。

| 机制 | 解决的问题 | 本质 |
|---|---|---|
| `clk` | 寄存器何时同步更新 | 节拍同步 |
| `start / finish` | 一次任务何时开始、何时结束 | 任务同步 |

更直观地说：

- `clk` 说：大家按统一节拍行动；
- `start` 说：这次任务现在开始；
- `finish` 说：这次任务已经结束，结果有效。

所以 `clk` 是电路运行的时间基准，握手是模块之间的协作协议。

如果只有 `clk`，模块之间只能靠“等几拍”来猜结果是否完成；有了握手，外部不需要猜时间，只需要看状态信号。

这就是握手协议最重要的思想：

> ==用状态确认替代时间猜测。==

---

## 3. start-finish 协议的基本规则

最简单的握手协议就是 `start / finish`。

一次完整任务大致经过四步：

1. 调用者准备好输入数据；
2. 调用者拉高 `start`，表示“任务开始”；
3. 被调用模块锁存输入，进入内部计算；
4. 计算完成后，被调用模块拉高 `finish`，表示“结果有效”。

在实验中的语义可以写成：

```text
caller:  输入有效 + start = 1
callee:  锁存输入，开始计算
callee:  finish = 1，输出结果有效
caller:  读走结果，再发起下一次 start
```

需要注意两点。

第一，`start` 不是普通输入数据的一部分，而是一个**控制语义**：它告诉模块“现在这组输入应该被接收”。没有 `start`，输入线上的值即使变化，也不应该被当成新任务。

第二，`finish` 也不是普通输出数据的一部分，而是一个**有效性标志**：它告诉外部“现在输出结果可以读”。没有 `finish`，输出线上的值即使有变化，也不应该被认为是最终结果。

因此，握手协议把数据和数据的有效性分开了。

这点很关键。硬件连线一直都有值，但不是所有值都有意义。`start / finish` 的作用，就是给这些值标注语义边界。

---

## 4. 握手的本质：隐藏内部时间

握手协议最核心的价值是：**隐藏内部完成时间**。

外部不需要知道乘法器到底是：

- 16 拍完成；
- 32 拍完成；
- 提前结束；
- 未来改成流水线；
- 或者某些输入快、某些输入慢。

外部只需要遵守一条规则：

> 发出 `start` 后，等待 `finish`，`finish` 有效时读取结果。

这就把“内部怎么计算”封装起来了。

从模块化角度看，结构接口隐藏的是**空间实现细节**，比如内部用了几个寄存器、几个加法器；握手协议隐藏的是**时间实现细节**，比如内部跑了多少拍、什么时候完成。

所以握手协议本质上也是一种接口设计，只不过它不是数据接口，而是时间接口。

---

## 5. FSM 如何承载握手语义

实验里的乘法器、除法器一般都会写成三态 FSM：`IDLE / WORK / FINAL`。

```verilog
IDLE: begin
    if (start) begin
        // 锁存输入
        // 初始化寄存器和计数器
        next_state = WORK;
    end
end

WORK: begin
    // 每拍执行一轮迭代
    if (work_done)
        next_state = FINAL;
end

FINAL: begin
    // 输出结果有效
    next_state = IDLE;
end
```

三个状态分别对应三种对外语义。

| 状态 | 内部含义 | 对外语义 |
|---|---|---|
| `IDLE` | 空闲等待 | 可以接收新任务 |
| `WORK` | 正在计算 | 输入已锁存，结果未完成 |
| `FINAL` | 计算完成 | 输出有效，`finish = 1` |

通常可以直接让 `finish` 由状态决定：

```verilog
assign finish = (fsm_state_reg == FINAL);
```

这说明 `finish` 不是随便拉高的信号，而是 FSM 对外暴露出的“当前处于完成状态”。

换句话说，FSM 不只是控制内部数据通路，它还在维护模块对外的协议语义。

---

## 6. 为什么要先锁存输入

在 `start` 有效时，模块通常要立刻把输入数据锁存进内部寄存器，例如：

```verilog
if (start) begin
    multiplicand_reg <= multiplicand;
    multiplier_reg   <= multiplier;
    fsm_state_reg    <= WORK;
end
```

原因很简单：外部输入线不是模块内部的一部分，调用者后面可能会改变它。

如果不锁存输入，而是在 `WORK` 状态里一直直接读取外部输入，那么计算过程中外部输入一变，内部正在计算的数据也会跟着变。这样一次任务就不再对应一组稳定输入，结果没有意义。

所以 `start` 的实际含义更精确地说是：

> 当前输入有效，请在这一拍把它们采样并保存下来。

这也是时序电路里非常重要的边界意识：

> ==外部信号只在协议规定的时刻可信。==

`start` 给输入数据划定了可信时刻，`finish` 给输出数据划定了可信时刻。

---

## 7. 为什么完成前不能再次 `start`

简单的 `start / finish` 协议通常默认一次只能处理一个任务。

也就是说：

> 上一次 `finish` 出现之前，不应该发起下一次 `start`。

原因是这个模块内部只有一套工作寄存器。如果还在 `WORK` 状态时再次 `start`，新的输入会覆盖旧任务的数据，导致前一次计算被破坏。

所以这种协议本质上是**单事务协议**：同一时间只允许一个任务在模块内部执行。

如果想支持连续发起多个任务，就需要更复杂的机制，例如：

- `ready / valid` 双向握手；
- 输入队列 FIFO；
- 流水线寄存器；
- 多任务 tag 标记。

但在 Lab3 这种迭代乘法器/除法器里，`start / finish` 已经足够。它牺牲吞吐量，换来控制逻辑简单、语义清楚。

## 8. Testbench 中 `wait(finish == 1)` 的意义

实验中常见的测试写法是：

```verilog
repeat (16) begin
    @(posedge clk);
    multiplicand = $random;
    multiplier   = $random;
    start        = 1;

    wait(finish == 1);
    @(posedge clk);
end
```

`wait(finish == 1)` 的含义是：当前执行流暂停，直到 `finish` 为 1。

它不是等固定时间，也不是猜模块要运行多少拍，而是直接等待模块自己给出完成信号。

这和真实使用场景是一致的：

- 人按按钮后等数码管显示结果；
- CPU 发起外设操作后等完成标志；
- 网络通信中发送方等 ACK；
- 软件异步任务中 caller 等 callback 或 promise resolve。

这些场景本质都一样：调用者不应该假设对方什么时候完成，而应该等待对方明确告诉自己“完成了”。

---

## 9. 为什么 `wait` 比固定 `#delay` 更好

固定延迟的写法可能是：

```verilog
#1000;
```

这种写法的问题是：它把测试逻辑和内部实现绑定死了。

如果模块本来 32 拍完成，`#1000` 可能刚好够；但如果以后模块改了：

- 计算更快，`#1000` 浪费时间；
- 计算更慢，`#1000` 读到错误结果；
- 不同输入耗时不同，固定 delay 根本不可靠。

而 `wait(finish == 1)` 依赖的是协议，不依赖内部耗时。只要模块遵守“完成后拉高 `finish`”这个契约，测试就不用改。

这就是协议设计带来的稳定性。

---

## 10. 最后一个 `@(posedge clk)` 为什么不多余

很多人容易疑惑：

```verilog
wait(finish == 1);
@(posedge clk);
```

既然已经等到 `finish`，为什么还要再等一个时钟上升沿？

因为 `wait(finish == 1)` 解除时，FSM 仍然处于 `FINAL` 状态。`FINAL -> IDLE` 的跳转要等下一个 `posedge clk` 才会发生。

如果不等这一拍，testbench 可能立刻发起下一次 `start`。这时模块还没回到 `IDLE`，新的 `start` 可能被忽略，或者和状态跳转发生竞争。

所以多等一拍的作用是：

> 确保模块完成 `FINAL -> IDLE` 的状态恢复，再发起下一次任务。

这不是多余等待，而是在维护协议边界。

---

## 11. 为什么 `wait` 不容易漏掉 `finish`

`wait(finish == 1)` 是**电平敏感**的。

只要 `finish` 当前值为 1，`wait` 就会通过；如果当前不是 1，它会在相关信号变化后重新判断。

这和边沿敏感写法不同：

```verilog
@(posedge finish);
```

`@(posedge finish)` 只等一个上升沿。如果进程执行到这一行之前，`finish` 已经从 0 变成 1，那么这个边沿就已经错过了，进程可能永远等不到下一次上升沿。

而 `wait(finish == 1)` 关心的是状态本身，不关心你有没有刚好卡在跳变那一瞬间。

所以对于“等待完成状态”这种语义，`wait(finish == 1)` 通常比 `@(posedge finish)` 更稳。

---

## 12. 仿真事件调度：为什么 finish 会被 wait 看见

SystemVerilog 仿真中，同一个时间点内部还有调度顺序。

常见理解是：

- Active 区处理组合逻辑、阻塞赋值、`$display`；
- NBA 区统一更新非阻塞赋值 `<=`。

假设 FSM 在某个时钟沿执行：

```verilog
fsm_state_reg <= FINAL;
```

这个赋值不会立刻改变 `fsm_state_reg`，而是在 NBA 区统一更新。状态更新后，组合逻辑重新计算：

```verilog
assign finish = (fsm_state_reg == FINAL);
```

于是 `finish` 变成 1。

由于 `wait(finish == 1)` 是电平敏感的，只要 `finish` 变成 1 并保持至少一个周期，它就会在重新判断时通过。

这也是为什么实验里要求 `finish` 至少保持一个周期。只打一瞬间的脉冲，调用者未必能稳定采到；保持一个周期，语义就清楚得多。

## 13. 下板场景中的握手直觉

仿真里，`start` 可能来自 testbench；下板时，`start` 可能来自按钮。

按钮按下表示“开始一次计算”，模块内部进入 `WORK`；完成后 `finish` 拉高，结果显示在数码管上。

这里人的反应速度远慢于电路速度。电路可能几十个周期就算完，但人下一次按按钮通常已经隔了几百毫秒。这天然满足“上一次完成前不发起下一次 start”。

但是这不意味着协议不重要。恰恰相反，按钮只是低速场景下的 caller，FSM 是 callee。人和电路之间依然需要一个清晰语义：

- 按钮触发 `start`；
- 模块锁存输入；
- 计算完成后 `finish` 有效；
- 显示模块读取结果。

如果没有这层协议，按钮、电路、显示之间就只能靠时序凑巧配合。

---

## 14. 常见错误：把 `start` 当成普通电平

`start` 最好理解为“一次请求”，不是一个长期使能信号。

如果 `start` 一直保持为 1，而 FSM 在 `FINAL` 后回到 `IDLE`，就可能马上再次进入 `WORK`，导致同一组输入被重复计算。

所以实际设计中通常要保证：

- `start` 至少保持一个周期，让模块能采到；
- 但最好只形成一个周期的脉冲；
- 如果来自按钮，还需要消抖和边沿检测。

这就是为什么下板实验里按钮通常要经过 `Debouncer`，甚至还要做单脉冲生成。按钮的物理电平不是协议本身，电路要把它整理成清晰的 `start` 请求。

---

## 15. 常见错误：在 `finish` 前读取结果

另一个常见错误是：计算还在 `WORK` 状态，就去读取 `product` 或 `quotient`。

这时输出寄存器可能还是中间值，不是最终结果。

硬件连线任何时候都有值，但这个值不一定有效。`finish` 的意义就是告诉外部：

> 从现在开始，输出才具有最终结果语义。

所以不要把“线上有值”和“结果有效”混为一谈。

这也是数字系统里非常重要的一条思维：

> ==数据必须配合有效信号才有意义。==

---

## 16. 思维提升：协议是时间维度的模块化

模块化通常被理解为“把电路拆成不同模块”。但更深一层看，模块化真正要解决的是边界问题：哪些东西对外暴露，哪些东西内部隐藏。

普通接口隐藏的是结构细节，握手协议隐藏的是时间细节。

没有握手时，外部必须知道内部跑几拍；有了握手后，外部只知道：

```text
start 发出请求
finish 返回完成
```

中间过程全部封装在模块内部。

这就是时间维度的模块化。

外部不关心内部跑 32 拍还是 16 拍，不关心有没有提前结束，也不关心内部状态机怎么写。只要 `start / finish` 的行为承诺不变，内部实现就可以独立修改。

所以握手协议的本质不是两根线，而是一种工程化思想：

> ==不要让调用者依赖被调用者的内部时间。==

---

## 17. 和软件、系统设计的类比

握手协议在计算机系统里到处都是。

CPU 访问外设时，不会假设外设几拍后必定完成，而是看 ready/busy 标志。网络通信里，发送方不会假设数据一定送达，而是等 ACK。软件异步任务里，调用者不会阻塞猜时间，而是等待回调、事件或 future 完成。

这些东西形式不同，但本质一样：

> 发起请求，等待确认，再使用结果。

Lab3 里的 `start / finish` 是这个思想的最小硬件版本。

学这个实验不只是为了会写 FSM，而是为了建立一种协议意识：模块之间不能靠猜测合作，必须靠明确的接口语义合作。

---

## 18. 一句话总结

`clk` 解决“大家什么时候同步更新”，握手解决“一次任务什么时候有效完成”。`start / finish` 把内部不确定的计算时间封装起来，让外部通过协议而不是猜测来使用模块。
